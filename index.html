What is a parser?

less-structured input -> more-structured output

Which is an incredibly powerful tool

They allow discharging checks on input up-front,
at the boundary

Once these checks have been passed,
they never need to happen again.

Doing these checks up-front can prevent a whole class of bugs

Some of which might even be security vulnerabilities

One drawback:

there can be a lot of distance between parsing and processing

The danger of validation

Is it really that bad?

Ad-hoc validation leads to shotgun parsing

Ad-hoc validation leads to shotgun parsing

Shotgun parsing is a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code—throwing a cloud of checks at the input, and hoping, without any systematic justification, that one or another would catch all the “bad” cases.
  • Late-discovered input errors lead to parts of it being processed
  • Program state becomes difficult to accurately predict

How is this related to validation?

If I just do all my validation up front, surely I will mitigate the risk of shotgun parsing

Right?

Validation based approaches make it extremely difficult to determine if everything was actually validated up front

You must assume throwing exceptions anywhere is regularly necessary

Exceptions are not tracked by the type system 3

3 Java has checked exceptions which are actually tracked

Opinions are plentiful and divided

see also: The trouble with checked exceptions

Parsing avoids this problem

by splitting the program into 2 phases

  • Parsing
  • Execution

How?

Focus on the datatypes

Consider a function that accepts an array of key value tuples

But you aren't sure what to do when encountering duplicate keys

This is fragile

  • It can be omitted / forgotten
  • The code that consumes the array would typecheck regardless

What would be a better solution?

Have the function accept a Map<Key, Value> instead
Keep changing the type from Array to Map all the way up the call chain, eventually you'll reach the location the value is created or you'll find a place where duplicates actually ought to be allowed.

Now the check cannot be omitted

Its result is needed for the program to proceed

Two simple ideas highlighted

  1. use a data structure that makes illegal states unrepresentable
  2. Push the burden of proof upward as far as possible, but no further

Additional advice

  1. Let your datatypes inform your code, don't let your code control your datatypes
  2. Treat functions that return void with deep suspicion
  3. Don't be afraid to parse data in multiple passes
  4. Avoid denormalized representations of data, especially if it's mutable
  5. Use abstract datatypes to make validators "look like" parsers 4
4 In typescript, this is harder to do as it uses structural typing.
